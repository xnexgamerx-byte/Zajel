# دراسة مقارنة: أنظمة التوصيل مفتوحة المصدر على GitHub (سبتمبر 2026)

> بحث ميداني لاختيار مرجع تقني لمشروع **زاجل**.
> المتطلب: منصة توصيل متكاملة فيها **نظام للمندوبين** + **نظام لخدمة الزبائن** + **نظام للتجار** الذين يرسلون طلباتهم + لوحة إدارة.
> كل المعلومات أدناه تم التحقق منها باستنساخ المستودعات وقراءة الكود والرخص فعلياً، لا من أوصاف الصفحات فقط.

## 3. التحليل التفصيلي

### 3.1 🥇 Fleetbase — الأكمل والأفضل للدراسة
**`github.com/fleetbase/fleetbase`** · 3,811⭐ · AGPL-3.0 + رخصة تجارية

نظام تشغيل لوجستي (Logistics OS) معياري، وليس مجرد تطبيق توصيل. هذا بالضبط ما تحتاجه شركة توصيل.

**البنية المعمارية** (تم التحقق منها من الكود):
- `api/` — Laravel 10 + Octane، يجمّع الإضافات عبر Composer
- `console/` — لوحة التحكم بـ Ember.js
- `packages/` — إضافات مستقلة (submodules): `fleetops`, `storefront`, `customer-portal`, `ledger`, `pallet`, `iam-engine`, `ai`, `registry-bridge`
- خدمات Docker: `application`, `console`, `database`, `cache`, `queue`, `scheduler`, `socket`, `httpd`

**نموذج البيانات في FleetOps** — هذه أهم قيمة للدراسة، نماذج إنتاجية حقيقية:
```
Order, OrderConfig, Payload, Entity, Manifest, ManifestStop
Driver, Fleet, FleetDriver, Vehicle, FleetVehicle
Place, Position, Route, ServiceArea, Geofence, GeofenceEventLog
Proof (إثبات التسليم), ServiceRate, ServiceQuote, ServiceRateParcelFee
Telematic, Device, FuelReport, Maintenance, Issue, InspectionForm
Contact, Customer, IntegratedVendor
```
> **`OrderConfig` تحديداً هو الفكرة الذهبية**: يسمح بتعريف دورة حياة الطلب ومراحلها كإعدادات (Configuration) بدل كتابتها في الكود — لأن دورة حياة توصيل الطعام تختلف عن الطرود عن الشحن. لو بنيت هذا في زاجل من البداية توفر عليك إعادة كتابة النظام لاحقاً.

**الأنظمة الأربعة المطلوبة موجودة كلها**:
| النظام | أين |
|---|---|
| المندوبون | `fleetbase/navigator-app` — React Native + Mapbox: استلام الطلب، ملاحة، توقيع رقمي، صور، QR، إثبات تسليم، محادثة مع العمليات والزبون، تقارير وقود |
| التجار | `fleetbase/storefront` — منتجات ومتغيرات وأسعار وساعات عمل وطلبات، ودعم **شبكات متعددة البائعين** (متجر واحد أو شبكة متاجر) |
| الزبائن | `fleetbase/storefront-app` (تطبيق) + `customer-portal` (بوابة تتبع ذاتية) |
| خدمة الزبائن | محادثة مدمجة + تعليقات على الطلبات + إشعارات + صلاحيات RBAC + تحقق ثنائي |

**نقاط القوة**: نشاط استثنائي (إصدارات كل بضعة أيام)، تحسين مسارات حقيقي عبر VROOM و Valhalla، بوابات دفع متعددة تشمل **الدفع عند الاستلام**، ترجمة عربية موجودة، معمارية إضافات تسمح ببناء وحداتك الخاصة.

**نقاط الضعف**:
1. **AGPL-3.0** — لو عدّلت الكود وقدّمته كخدمة SaaS، الرخصة تُلزمك بنشر مصدر تعديلاتك لمستخدميك. لتجنب ذلك تحتاج الرخصة التجارية. ← **هذه أهم نقطة قانونية في البحث كله، انتبه لها قبل البناء عليه.**
2. Ember.js في الواجهة تقنية قليلة الانتشار اليوم؛ التوظيف عليها صعب.
3. حجمه وتعقيده كبيران — منحنى تعلم حاد.

### 3.3 🥉 codflow — الأحدث والأقرب لواقع السوق العربي
**`github.com/bighadj22/codflow`** · 277⭐ · Apache-2.0 · أُنشئ 2026-08-20

منصة تجارة إلكترونية ولوجستيات مبنية أصلاً حول **الدفع عند الاستلام (COD)** — وهو النموذج السائد في العراق والجزائر وأغلب المنطقة، وليس الدفع الإلكتروني الذي تفترضه المشاريع الغربية.

**البنية**: `cod-server` (Hono 4 على Cloudflare Workers) + `cod-client-astro` (لوحة التاجر) + `cod-astro` (المتجر) + `cod-shared`
**قاعدة البيانات**: Cloudflare D1 (SQLite) + Drizzle ORM
**نقاط API تم التحقق منها**: `orders`, `driver-payments`, `stores`, `customers`, `customer-groups`, `offers`, `reviews`, `abandoned-orders`, `wilayas`, `store-otp`, `landing-pages`
**مجلدات مهمة**: `rbac/`, `workflows/`, `mcp/`, `cron/`, `db/migrations/`

**ما يستحق النسخ منه لزاجل**:
- تقسيم جغرافي بمستوى **الولاية/المحافظة** مع تسعير وأجور مندوب مختلفة لكل منطقة
- **تسوية نقدية** مع المندوبين (`driver-payments`) — مشكلة حقيقية لا تحلها الأنظمة الغربية
- تحقق من الزبون عبر **WhatsApp OTP** قبل تأكيد الطلب (يقلل الطلبات الوهمية، أكبر وجع في COD)
- تكامل مع شركات شحن محلية (Yalidine, ZR Express, NOEST, EcoTrack)
- **عربي / فرنسي / إنجليزي مع RTL كامل** من أول يوم

**الحدود**: لا يوجد تطبيق موبايل للمندوب (الإدارة من لوحة التاجر)، ولا وحدة مركز اتصال/خدمة زبائن، ومركزه التاجر الفردي لا شركة التوصيل. مرتبط بنظام Cloudflare البيئي.

### 3.4 Ever Demand — طموح لكنه alpha
**`github.com/ever-co/ever-demand`** · 1,859⭐ · AGPL-3.0

منصة TypeScript كاملة (NestJS + GraphQL + MongoDB + Angular + Ionic) بكل الأدوار: تطبيق تسوق، **تطبيق ناقل/مندوب**، **تطبيق تاجر لوحي**، لوحة إدارة، وموقع.

### 3.5 Siam Cloud / Siam Server — كامل الأدوار لكن حاجز اللغة
**`github.com/siam1026/siam-cloud`** · 340⭐ · Apache-2.0

نظام صيني بأربعة أطراف بالضبط: مستخدم + تاجر + **مندوب توصيل** + إدارة، على Spring Cloud Alibaba + Vue/Element + uni-app، مع Redis و RocketMQ و WebSocket و ElasticSearch.

**العائق**: التوثيق والكود بالصينية بالكامل، و**بعض الموارد (ملفات SQL، البرنامج المصغّر للتاجر، نظام إدارة المندوبين) تتطلب الانضمام لمجموعات QQ/WeChat** — أي أنه ليس مفتوحاً بالكامل عملياً.

## 5. خطة دراسة عملية مقترحة (بالترتيب)

**المرحلة 1 — نموذج البيانات (الأهم):**
1. `fleetops/server/src/Models/Order.php` و `OrderConfig.php` — كيف تُعرّف دورة حياة الطلب كإعدادات
2. `Payload.php` + `Entity.php` — كيف يُمثَّل محتوى الشحنة (طرد، وجبة، عدة أصناف)
3. `ServiceRate.php` + `ServiceQuote.php` — محرك التسعير حسب المسافة/المنطقة/الوزن
4. `Proof.php` + `Position.php` — إثبات التسليم والتتبع اللحظي

**المرحلة 2 — تطبيق المندوب:**
5. `fleetbase/navigator-app` — تدفق: استلام مهمة ← ملاحة ← تحديث حالة ← إثبات تسليم
6. `enatega-multivendor-rider/app/` — قارن تنظيم الشاشات و`chat/`

**المرحلة 3 — التاجر وخدمة الزبائن:**
7. `fleetbase/storefront` — شبكات البائعين المتعددين والعقد بينهم
8. `fleetbase/customer-portal` — التتبع الذاتي للزبون (يقلل ضغط الاتصالات 70%)

**المرحلة 4 — الخصوصية المحلية:**
9. `codflow/cod-server/src/endpoints/driver-payments` — تسوية النقد مع المندوبين
10. `codflow/cod-server/src/rbac/` + `workflows/` — الصلاحيات والعمليات غير المتزامنة

## 6. فجوات لن تجدها جاهزة في أي مشروع

هذه لا يغطيها أي من المشاريع أعلاه وستحتاج بناءها بنفسك في زاجل:

1. **مركز اتصال / خدمة زبائن حقيقي** — تذاكر، تسجيل مكالمات، ربط المحادثة بالطلب، حالة "مشكلة في الطلب". أقرب شيء موجود هو محادثة Fleetbase.
2. **تأكيد الطلبات الهاتفي** — في أسواق COD نسبة الإلغاء عالية، وفرق التأكيد جزء أساسي من العملية.
3. **المحاسبة النقدية اليومية** — تحصيل المندوب، عهدته، التسوية في نهاية اليوم. `codflow` يلمسها فقط.
4. **التسعير حسب المحافظة/المنطقة بالعُرف المحلي** والتفاوض مع التجار على العمولة.
5. **العمل دون إنترنت** لتطبيق المندوب في مناطق التغطية الضعيفة.

## 7. ملاحظة قانونية مهمة

- **MIT** (Enatega frontends) و **Apache-2.0** (codflow, Siam) → حرية كاملة للاستخدام التجاري دون التزام بنشر كودك.
- **AGPL-3.0** (Fleetbase, Ever Demand) → إذا عدّلت وقدّمت خدمة عبر الشبكة، **تلتزم بإتاحة مصدر تعديلاتك لمستخدميك**. Fleetbase يوفر رخصة تجارية بديلة مدفوعة.

**الخلاصة العملية**: ادرس Fleetbase معمارياً واستلهم منه، وانسخ الكود فعلياً من Enatega (MIT) و codflow (Apache-2.0)، أو اشترِ الرخصة التجارية لـ Fleetbase إن قررت البناء المباشر عليه.
