# التسليم للطرف الثالث: ربط الشركة الصغيرة بالشركة الكبيرة

> السيناريو: شركة في بغداد فقط، تريد تغطية كل العراق، فتسلّم شحناتها لشركة لها فروع،
> وتأخذ ربحها عن كل قطعة واصلة.
> **اسم المشكلة في اللوجستيات: Interlining / Sub-contracting.**
> 2026-09-21

---

## ١. 🎉 المصدر يحلّ هذا أصلاً — أربع قطع جاهزة

فحصتُ الكود فوجدتُ البنية كاملة تقريباً. هذه ليست ميزة ستبنيها من الصفر:

### القطعة ١: الشركة تعلن أين تخدم
`ShippingCompany`:
```php
'served_countries',   // الدول المخدومة
'served_cities',      // ← المدن المخدومة
```
> شركتك تقول: "أخدم بغداد فقط".

### القطعة ٢: قاعدة التحويل للشريك — **قلب السيناريو**
`ShippingFallbackRule`:
```php
'unserved_city_id',              // المدينة غير المخدومة
'fallback_shipping_company_id',  // الشركة البديلة التي تستلمها
'priority',                      // الأولوية عند وجود عدة شركاء
```
> **هذا حرفياً سؤالك**: «البصرة غير مخدومة عندي → حوّلها إلى شركة س بأولوية ١».
> والأولوية تعني: إن رفضت س، جرّب ص.

### القطعة ٣: الناقل الشريك بمفاتيح الربط
`ShippingCarrier`:
```php
'shipping_company_id',      // الشركة المالكة لهذا الربط
'code', 'name',
'api_endpoint',             // ← عنوان API الشريك
'credentials_encrypted',    // ← مفاتيحه مشفّرة
'tracking_url_pattern',     // ← صفحة تتبعه
'supports_cod',             // ← هل يدعم الدفع عند الاستلام
'supports_returns',         // ← هل يدعم المرتجعات
```

### القطعة ٤: طبقة المحوّلات (Adapter Pattern) — مبنية بالفعل
```
app/Contracts/ShippingCarrierInterface.php     ← العقد المشترك
app/Services/Shipping/ShippingCarrierFactory.php ← السجل والمُحلِّل
app/Services/Shipping/Carriers/
    ├── AramexCarrier.php
    ├── BostaCarrier.php
    ├── DhlCarrier.php
    ├── FedexCarrier.php
    └── ManualCarrier.php     ← ⭐ للشركاء بلا API
```

**العقد الذي ينفّذه كل محوّل — سبع دوال فقط:**
```php
getCode() : string
getName() : string
createShipment(SubOrder, options) : ShippingLabel   // إنشاء الشحنة وإصدار البوليصة
getTracking(trackingNumber)      : TrackingResult   // سحب أحداث التتبع
cancelShipment(Shipment)         : bool             // الإلغاء/الإرجاع
calculateRate(from, to, weight, dims, currency)     // { rate, currency, estimated_days, service_name }
testConnection()                 : array            // { success, latency_ms, message }
supportsCod()                    : bool
```

> **إضافة شريك عراقي جديد = ملف واحد** ينفّذ هذه الدوال السبع، وسطر تسجيل في المصنع.

## ٢. كيف يجري سيناريوك خطوة بخطوة

```
١. التاجر ينشئ شحنة إلى البصرة على نظام شركتك
          ↓
٢. النظام يقرأ served_cities → البصرة غير مخدومة
          ↓
٣. يقرأ ShippingFallbackRule → الشريك "شركة س" (أولوية ١)
          ↓
٤. يستدعي ShippingCarrierFactory::make('sharika_s')
          ↓
٥. calculateRate()  → تكلفة الشريك عليك
   createShipment() → بوليصة الشريك + رقم تتبعه
          ↓
٦. تُحفظ في Shipment:
      carrier_id · tracking_number · awb_label_url · shipping_cost_actual
          ↓
٧. getTracking() دورياً → تحديث حالة الشحنة عندك
          ↓
٨. عند التسليم: ربحك = (ما دفعه التاجر) − (shipping_cost_actual)
```

**والتاجر لا يرى شيئاً من هذا** — يرى رقم تتبع واحداً باسم شركتك. وهذه نقطة بيع قوية للشركة الصغيرة.

## ٣. الشركة الكبيرة — ثلاث حالات، وكلها مغطّاة

| الحالة | الحل | الجهد |
|---|---|---|
| **عندها API** | محوّل جديد بنفس نمط `AramexCarrier` | يوم–يومان لكل شريك |
| **عندها بوابة ويب فقط** | محوّل يصدّر CSV/Excel للرفع اليدوي، ويستورد ملف التتبع | ٢–٣ أيام |
| **لا يوجد شيء** | `ManualCarrier` **جاهز** — الشحنة تُسجَّل، والتسليم بمانيفست ورقي/PDF، وأرقام التتبع تُدخَل يدوياً أو بمسح باركود | **صفر** |

> `ManualCarrier` هو المفتاح للسوق العراقي: أغلب الشركات المحلية بلا API، ومع ذلك **تدخل النظام من اليوم الأول عبر نفس الواجهة**. ثم تبني لها محوّلاً حقيقياً حين يتوفر API — بلا تغيير في بقية النظام.

## ٤. 🎯 الميزة الاستراتيجية — وهي أهم مما يبدو

سألتَ: «الشركات الكبيرة أكيد عندهم نظام نفس اللي عندي».
صحيح. **وهنا تكمن الفرصة لا العقبة.**

### إن كانت الشركتان على زاجل
التسليم لا يصبح **تكاملاً خارجياً** بل **عملية داخلية**:
```
شركة صغيرة (بغداد)  ──[تسليم داخلي في زاجل]──→  شركة كبيرة (فروع)
        بلا API · بلا ملفات · بلا مطابقة حالات · تتبع موحّد لحظي
```
لأن الطرفين على نفس المخطط ونفس رموز الحالات. **التكامل يختفي كمشكلة.**

### وهذا يقلب استراتيجية دخولك للسوق

**لا تبدأ بإقناع الشركات الكبيرة** — هذا صعب وبطيء. بل:

```
١. اجلب الشركات الصغيرة   ← سهل: أكثرها بلا نظام أصلاً، وأنت تحلّ لها أكبر وجع
                              (التغطية خارج مدينتها)
٢. هذه الشركات تدفع حجماً  ← الشحنات المحوَّلة تتراكم نحو الشركات الكبيرة
٣. الشركة الكبيرة تكتشف    ← «٤٠٪ من شحناتي تأتيني من شركات على زاجل»
٤. فتنضم هي               ← لتستلم آلياً بدل الاستلام اليدوي
٥. أثر الشبكة يكتمل        ← كل شركة جديدة تزيد قيمة المنصة لمن قبلها
```

> **الشركات الصغيرة هي حصان طروادة الذي يُدخلك على الكبار.**
> وهذا أيضاً جوابك على خطر التسرّب في المستند السابق: من يترك زاجل يفقد شبكة الشركاء كلها، لا برنامجاً فقط.

## ٥. فجوتان حقيقيتان يجب بناؤهما

فحصتُ الكود ووجدتُ نقصين يخصّان هذا السيناريو تحديداً:

### الفجوة ١: لا يوجد مانيفست تسليم بالجملة
بحثتُ عن `Manifest` / `Handover` / `Consignment` في النماذج: **غير موجودة**.

**ما تحتاجه**: عند تسليم ٥٠ شحنة دفعةً واحدة للشريك:
```
HandoverManifest
  ├── carrier_id · created_by · created_at
  ├── shipments[]           (الشحنات المسلَّمة)
  ├── status                (مُجهَّز · مُسلَّم · مُستلَم · متنازَع عليه)
  ├── received_by · received_at · signature/photo
  └── discrepancies[]       (نواقص أو تلف عند الاستلام)
```
هذا مستند قانوني ومالي بينك وبين الشريك — بلا وجوده، كل خلاف يصبح كلمة ضد كلمة.

### الفجوة ٢: الهامش لكل قطعة غير محسوب
`Shipment` يحمل **التكلفة فقط**:
```php
'shipping_cost_actual',   // ما دفعتَه للشريك  ✅
// لا يوجد حقل لما حصّلتَه من التاجر  ❌
```
**ما تحتاجه** على الشحنة:
```
revenue_charged     ما حصّلته من التاجر
partner_cost        ما دفعته للشريك  (= shipping_cost_actual)
margin              الفرق — محسوب ومخزَّن
```
وكل ذلك يُقيَّد في `LedgerEntry` (القيد المزدوج الموجود أصلاً):
```
مدين: ذمم التاجر          revenue_charged
دائن: إيراد الشحن          revenue_charged
مدين: تكلفة الشحن          partner_cost
دائن: ذمم الشريك           partner_cost
```
> بلا هذا الفصل، لن تعرف الشركة ربحها الحقيقي لكل خط شحن — وهي أهم معلومة عندها.

### وثالثة أقل إلحاحاً: مطابقة الحالات
كل شريك يسمّي حالاته باسمه (`in_transit` / `out_for_delivery` / «بالطريق»).
تحتاج جدول `carrier_status_map` يترجم حالات كل شريك إلى حالات زاجل الموحّدة.

## ٦. نموذج الإيراد في هذه الحالة

سألتَ: اشتراك شهري/سنوي أم عمولة على كل شحنة؟

| النموذج | الحكم |
|---|---|
| اشتراك ثابت | 🟡 بسيط، لكنه يثقل على الصغير ويُرخِص على الكبير |
| عمولة على كل شحنة | 🟢 عادل ويكبر مع العميل — لكن يحتاج ثقته بقياسك |
| **اشتراك أساسي + شريحة على الحجم** | ✅ **الأفضل** — أرضية ثابتة تغطي تكلفتك، وتصاعد عادل |

### ⚠️ ونصيحة مضادة للحدس: **لا تفرض رسماً على التسليم للشريك**

قد يبدو مغرياً أخذ عمولة على كل شحنة محوَّلة — لكن:
- هذه بالضبط **الميزة التي تمنع الشركة من تركك**
- وأي رسم عليها يدفعهم لإتمام التحويل خارج النظام (هاتف وواتساب)، فتفقد البيانات والتحكم معاً

> **اجعل التسليم للشريك مجانياً داخل الاشتراك.** هو خندقك الدفاعي، لا مصدر دخلك.

## ٧. الخلاصة

| السؤال | الجواب |
|---|---|
| هل أبني الربط من الصفر؟ | **لا** — `ShippingFallbackRule` + `ShippingCarrier` + طبقة المحوّلات موجودة |
| كيف أربط شريكاً عراقياً؟ | ملف محوّل واحد ينفّذ سبع دوال |
| وإن لم يكن لديه API؟ | `ManualCarrier` جاهز — يدخل النظام اليوم |
| والشركات الكبيرة على أنظمتها؟ | استقطب الصغار أولاً؛ حجمهم يجرّ الكبار إليك |
| ماذا أبني أنا؟ | **مانيفست التسليم** + **الهامش لكل شحنة** + **مطابقة الحالات** |
| كيف أسعّر؟ | اشتراك أساسي + شريحة حجم — **والتسليم للشريك مجاناً** |
