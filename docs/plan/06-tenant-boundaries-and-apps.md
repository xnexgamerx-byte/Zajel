# حدود المستأجر وربط تطبيقاته

> التأكيد: تطبيقات كل شركة ترتبط بنظامها، ونظامها **اشتقاق** من نظام زاجل الرئيسي،
> وللشركة حرية الاطّلاع والتحكم.
> 2026-09-21

---

## ١. حسم معنى «اشتقاق» — وهو قرار مصيري

للكلمة معنيان تقنياً، أحدهما يقتل المنتج:

### ❌ المعنى الخاطئ: نسخة كود منفصلة لكل شركة

```
زاجل الأصلي
   ├── نسخة شركة أ   (كود منفصل · قاعدة منفصلة · نشر منفصل)
   ├── نسخة شركة ب   (كود منفصل · قاعدة منفصلة · نشر منفصل)
   └── نسخة شركة ج   ...
```

**لماذا هذا انتحار**:
- ٢٠ شركة = **٢٠ نشراً و٢٠ قاعدة بيانات و٢٠ ترقيعاً** لكل إصلاح خطأ
- ثغرة أمنية واحدة = ٢٠ عملية ترقيع منفصلة
- النسخ **تتباعد** مع الوقت حتى تستحيل صيانتها
- تقاريرك المجمّعة كمشرف: **مستحيلة**
- بعد سنة: ثماني نسخ كود لا تستطيع تحديث أيٍّ منها

### ✅ المعنى الصحيح: **نسخة واحدة، اشتقاق منطقي**

```
        نواة زاجل  (كود واحد · نشر واحد · قاعدة واحدة)
                          │
      ┌───────────────────┼───────────────────┐
      ▼                   ▼                   ▼
  شركة أ              شركة ب              شركة ج
  a.zajel.iq          b.zajel.iq          c.zajel.iq
  شعارها وألوانها      شعارها وألوانها      شعارها وألوانها
  بياناتها فقط         بياناتها فقط         بياناتها فقط
```

**«نظام الشركة» = عرضٌ مُصفّى على النواة** بـ `carrier_id`.

الشركة **تحسّه نظامها الخاص بالكامل**: نطاقها الفرعي، علامتها، مستخدموها، بياناتها وحدها — ولا ترى شيئاً من غيرها. وأنت تحدّث **مرة واحدة** فيستفيد الجميع فوراً.

> **التشبيه**: بريد Gmail — كل شخص له «بريده الخاص»، والنظام واحد. لا أحد ينشئ نسخة Gmail لكل مستخدم.

## ٢. ربط التطبيقات — الخبر الجيد: التصميم صحيح أصلاً

فحصتُ `delivery_app/lib/core/api/api_client.dart`:
```dart
static const String baseUrl = 'https://api.example.com/api/delivery/v1';
```
**عنوان واحد، ولا ذكر للشركات إطلاقاً.** وهذا **بالضبط** التصميم الصحيح:

```
المندوب يسجّل الدخول
        ↓
الخادم يقرأ DeliveryAgent.shipping_company_id من رمز الدخول
        ↓
كل ما بعدها مُصفّى تلقائياً على شركته
```

> **التطبيق لا يحتاج أن يعرف شيئاً عن المستأجرين. الخادم هو من يعرف.**
> وهذا يجعل العزل غير قابل للتحايل من جهة العميل — تطبيق معدَّل لن يرى بيانات شركة أخرى.

### القرار العملي: تطبيق واحد أم تطبيق لكل شركة؟

| | **تطبيق واحد** ✅ | **تطبيق لكل شركة (White-label)** |
|---|---|---|
| على المتاجر | تطبيق واحد | تطبيق لكل شركة |
| إصلاح خطأ واحد | نشرة واحدة | **N نشرة + N مراجعة من Apple/Google** |
| حسابات المطوّرين | واحد | **واحد لكل شركة** |
| إطلاق شركة جديدة | **فوري** | ١–٣ أسابيع (مراجعة المتاجر) |
| التخصيص البصري | شعار وألوان تُحمَّل بعد الدخول | كامل |
| التكلفة | منخفضة وثابتة | **تتضاعف مع كل شركة** |

**ابدأ بتطبيق واحد.** المندوب يسجّل الدخول فيتحمّل **شعار شركته وألوانها** من الخادم — فيشعر أنه تطبيق شركته.

> ⚠️ **خطأ شائع**: الناس تظن White-label أمر تجميلي بسيط.
> الحقيقة: ٢٠ تطبيقاً تعني ٢٠ مراجعة متجر لكل إصلاح — **شهر كامل لنشر تصحيح سطر واحد.**
> اجعلها **ميزة مدفوعة للشركات الكبيرة فقط**، ومتأخرة.

### نفس المبدأ لباقي التطبيقات
| التطبيق | النمط |
|---|---|
| تطبيق المندوب | واحد · التخصيص بعد الدخول |
| لوحة/تطبيق التاجر | واحد · نطاق فرعي للشركة |
| لوحة شركة التوصيل | واحدة · `carrier.zajel.iq` |
| خدمة العملاء | واحدة · مُصفّاة بالمستأجر |
| **بوابة تتبع الزبون** | **بعلامة الشركة** — `tracking.zajel.iq/abc` أو نطاق الشركة نفسه |

> بوابة التتبع هي الاستثناء الذي **يستحق** التخصيص الكامل، لأن الزبون النهائي يراها وهي واجهة الشركة أمام السوق. وهي **صفحة ويب** لا تطبيق — فتخصيصها رخيص.

## ٣. الحدود: ما يملكه المستأجر وما يبقى مركزياً

هذا **العقد** بين النواة والمستأجر — احسمه مرة وثبّته:

### 🟢 حرية كاملة للمستأجر
```
مناديبه وفروعه ومناوباتهم
مستخدموه وأدوارهم وصلاحياتهم
تجاره وعقودهم وأسعارهم
شحناته وحالتها وتاريخها
تسعيره لتجاره
شعاره وألوانه ونطاقه الفرعي
ساعات عمله ومناطق تغطيته
تقاريره كاملة + تصدير بياناته متى شاء
قوالب إشعاراته ورسائله
```

### 🔵 مركزي — لا يمسّه المستأجر
```
المحافظات والمناطق والإحداثيات
رموز الحالات الموحّدة   ← ⚠️ حاسم: بلا توحيدها ينهار التتبع بين الشركات
شبكة النقل الوطنية (المراكز · الخطوط · الأكياس)
الخطط والاشتراكات والفوترة
بوابات الدفع والتكاملات الخارجية
تعرفة زاجل على الشركة
الأمان · النسخ الاحتياطي · التحديثات
سجل التدقيق
```

> **لماذا رموز الحالات مركزية؟** لأن الشحنة قد تمرّ من شركة صغيرة إلى شبكتك الوطنية.
> إن سمّت كل شركة حالاتها باسمها، فلن يستطيع أحد تتبّع شحنة عبر الحدود. **التوحيد شرط عمل لا تفضيل.**

## ٤. 🔑 القاعدة الذهبية: لا تفرّع الكود لشركة — أبداً

ستأتيك شركة وتطلب ميزة خاصة. **لا تنسخ الكود.** تعامل معها بهذا الترتيب:

| الحالة | الحل |
|---|---|
| الميزة تنفع الجميع | ابنِها للكل خلف **مفتاح ميزة (feature flag)** |
| خاصة بهذه الشركة | **إعداد (setting)** في لوحتها — لا كود |
| تحتاج منطقاً مختلفاً جذرياً | **وحدة إضافية (module)** تُفعَّل لها وحدها |
| لا تنسجم مع النموذج إطلاقاً | **اعتذر** — أو أجّلها حتى يطلبها ثلاثة عملاء |

> **أول تفريع تفعله هو بداية النهاية.** والمقاومة هنا أصعب مما تظن: العميل يدفع، والطلب يبدو بسيطاً.
> لكن ثمن «نعم» واحدة يُدفع كل شهر إلى الأبد.

## ٦. الخلاصة

| السؤال | الجواب |
|---|---|
| نظام كل شركة تابع لنظامي؟ | ✅ نعم — **اشتقاق منطقي لا نسخة كود** |
| تطبيقاتهم ترتبط بنظامهم؟ | ✅ نعم — **تلقائياً**، الخادم يحلّ المستأجر من رمز الدخول |
| كم تطبيقاً على المتاجر؟ | **واحد** لكل دور، والتخصيص البصري بعد الدخول |
| لهم حرية الاطّلاع والتحكم؟ | ✅ **كاملة داخل حدودهم** — الجدول في القسم ٣ |
| ماذا لو طلبوا تخصيصاً؟ | **إعداد أو مفتاح ميزة — لا تفريع كود أبداً** |

> **القاعدة الحاكمة**: نسخة واحدة تخدم الجميع، وكل شركة تراها نظامها وحدها.
> اللحظة التي تصبح فيها نسختان، تبدأ خسارتك.
