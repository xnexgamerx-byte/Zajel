# مواصفات النسخة الأولى — نظام إدارة شركة توصيل

> مستخلصة من تحليل النظام الحيّ (المستند ١٠) · العميل يطلب نظاماً مكافئاً
> 2026-09-21

---

## ١. تقدير الحجم بصدق — قبل أي وعد للعميل

| النظام المرجعي | الرقم |
|---|---|
| القوائم | ١٢ |
| الشاشات | ~١٠٠ |
| التقارير وحدها | ٣١ |
| سنوات البناء | **٢٠٢٢ → ٢٠٢٦ (أربع سنوات)** |
| الفريق | شركة بفريق كامل |

> **لا تَعِد العميل بـ«نفس النظام» في ثلاثة أشهر.** لن يحدث، وستخسر ثقته في الشهر الثاني.

### لكن — الجوهر أصغر بكثير من المئة شاشة
أغلب المئة **تنويعات وتقارير**: سبع طرق لإنشاء شحنة، و٣١ تقريراً، وأرشيفات.
**النواة التي تُشغّل شركة توصيل فعلياً: ٢٤ شاشة.**

## ٢. نموذج البيانات — ١٩ جدولاً

```
── الأساس ──────────────────────────────────
branches            الفروع (جذر تعدد المستأجرين)
users               موظفو الفرع
permissions         الصلاحيات
merchants           المتاجر/العملاء
── الأطراف الميدانية ───────────────────────
delivery_agents     مندوبو التوصيل
pickup_agents       مندوبو الاستلام      ← دور منفصل
zones               المناطق
agent_zones         توزيع المندوبين على المناطق
── الشحنة ──────────────────────────────────
shipments           الوصولات  ← الجدول المحوري
shipment_events     كل مراحل النقل (مصدر الحقيقة للتتبع)
── النقل ───────────────────────────────────
sacks               الأكياس
manifests           المنفيستات (مندوب · بين فروع)
manifest_items      محتوياتها
── المال ───────────────────────────────────
pricing             تسعيرات النقل (محافظة × نوع)
agent_accounts      حسابات المندوبين
merchant_accounts   حسابات العملاء
payments            الدفعات (واصل · راجع)
cash_boxes          القاصة والصناديق
expenses            المصروفات
```

### الحقول الجوهرية في `shipments`
```
branch_id            الفرع المالك        ← إلزامي في كل استعلام
merchant_id          التاجر
receipt_no           رقم الوصل (فريد لكل فرع)
barcode
recipient_name · recipient_phone
state_id · district_id · landmark        ← العلامة المميزة إلزامية (لا رمز بريدي)
amount               مبلغ الوصل (BIGINT بالدينار)
delivery_fee         أجرة التوصيل
amount_confirmed     هل أُكّد المبلغ (لا رجعة)
pickup_agent_id · delivery_agent_id
status · sack_id · manifest_id
collected_at · settled_at                ← تسوية النقد
created_by · created_at
```

### الحالات — موحّدة ومركزية
```
جديد → مستلم من التاجر → في المخزن → مُكيَّس → في الطريق لفرع
     → عند مندوب التوصيل → واصل | واصل إجباري | راجع → مُصفّى
```
> **`shipment_events` هو مصدر الحقيقة** — كل تغيير حالة صف جديد بـ(مَن · متى · أين · لماذا). كل شيء آخر اشتقاق منه.

## ٣. الشاشات — ٢٤ شاشة في ثلاث دفعات

### 🔹 الدفعة ١ — تشغيل الشركة (٦–٨ أسابيع) · ١٠ شاشات
| # | الشاشة | لماذا الآن |
|---|---|---|
| ١ | تسجيل دخول + صلاحيات | لا يبدأ شيء قبلها |
| ٢ | **إنشاء شحنة** (نموذج واحد فقط) | قلب النظام |
| ٣ | **رفع أكسل شحنات** | التاجر لا يُدخل ١٠٠ شحنة يدوياً |
| ٤ | **قائمة الشحنات** + بحث برقم الوصل | الشاشة الأكثر استخداماً |
| ٥ | تفاصيل الشحنة + سجل المراحل | |
| ٦ | إسناد لمندوب توصيل | |
| ٧ | **شاشة المندوب** (ويب متجاوبة) | واصل · راجع · سبب الفشل |
| ٨ | إدارة المتاجر | |
| ٩ | إدارة المندوبين (النوعان) | |
| ١٠ | **تسعيرات النقل** بالمحافظة | بلا تسعير لا محاسبة |

> **الناتج**: شركة تُدخل شحناتها وتوصّلها وتتتبعها. **نظام يعمل، لا عرض تقديمي.**

### 🔹 الدفعة ٢ — المال والراجع (٤–٦ أسابيع) · ٨ شاشات
```
١١  حساب المندوب + تسوية النقد     ← أخطر شاشة (٨.٦ مليون معلّقة ٣٧ يوماً)
١٢  حساب التاجر + كشف حساب
١٣  الدفعات (واصل)
١٤  استلام الراجع من المندوب
١٥  تسليم الراجع للتاجر
١٦  القاصة والصناديق
١٧  المصروفات
١٨  تأكيد مبلغ الوصل
```

### 🔹 الدفعة ٣ — الشبكة والتقارير (٤–٦ أسابيع) · ٦ شاشات
```
١٩  الأكياس (تكييس وفتح)
٢٠  المنفيستات (مندوب · بين فروع)
٢١  استلام منفيست وارد
٢٢  لوحة المعلومات (٦ بطاقات رقابية)
٢٣  تقارير أساسية (٦ لا ٣١)
٢٤  إعدادات الفرع + الصلاحيات
```

> **المجموع: ١٤–٢٠ أسبوعاً لنظام يشغّل شركة فعلياً** — لا ٤ سنوات، لأننا نبني النواة لا التنويعات.

## ٤. ستة تفاصيل تُبنى من اليوم الأول

هذه ليست ميزات متقدمة — إغفالها يعني إعادة بناء لاحقاً:

| # | التفصيل | السبب |
|---|---|---|
| ١ | **`branch_id` في كل جدول** | المستأجر الثاني بلا إعادة بناء |
| ٢ | **المبالغ BIGINT بالدينار** | لا `decimal` ولا قسمة على ١٠٠ |
| ٣ | **`landmark` إلزامي + GPS** | العراق بلا رموز بريدية |
| ٤ | **مندوب استلام ≠ مندوب توصيل** | دوران وحسابان منفصلان |
| ٥ | **`shipment_events` لكل تغيير** | التتبع والتدقيق والنزاعات |
| ٦ | **أسباب فشل مصنّفة** | لا حقل نصّي حر — الإحصاءات تُبنى عليها |

### ولمسات مجانية تقريباً ترفع القيمة كثيراً
مأخوذة من النظام المرجعي وتنفيذها ساعات لا أسابيع:
- **كشف الإيصالات المكررة** تلقائياً
- **«واصل إجباري» بحقل سبب إلزامي** — يمنع التلاعب
- **تأكيد مبلغ الوصل بنافذة لا رجعة** — ينهي نصف الخلافات المالية
- **إخفاء أرقام الزبائن** خلف زر يكشف رقماً واحداً في كل مرة
- **بحث عام برقم الوصل** في الشريط العلوي

## ٥. ما يُستبعد من النسخة الأولى صراحةً

أبلغ العميل بها **مكتوبةً** حتى لا تصبح خلافاً لاحقاً:

```
❌ سبع طرق لإنشاء الشحنة        → طريقتان (فردي + أكسل)
❌ ٣١ تقريراً                   → ستة
❌ تطبيقات موبايل               → ويب متجاوب (المندوب يفتحها على هاتفه)
❌ الباقات والاشتراكات          → الدفعة الرابعة
❌ الإشعارات الفورية (Push)     → واتساب/SMS أولاً
❌ حصص الاستلام واعتراضاتها     → بعد استقرار الأساس
❌ محاسبة الفروع وديونها        → عند وجود فرعين فعليين
❌ المحادثات والتذاكر           → الدفعة الرابعة
```

## ٦. ثلاثة أسئلة للعميل قبل تسعير العرض

| # | السؤال | لماذا يغيّر كل شيء |
|---|---|---|
| ١ | **كم فرعاً لديك الآن؟ وكم بعد سنة؟** | فرع واحد = أبسط كثيراً · عدة فروع = المنفيستات من الدفعة الأولى |
| ٢ | **كم شحنة في اليوم؟** | ١٠٠/يوم و٥٠٠٠/يوم نظامان مختلفان في البنية |
| ٣ | **لديك نظام حالي؟ وهل تُرحَّل بياناته؟** | الترحيل قد يعادل نصف المشروع — سعّره منفصلاً |

### وسؤال رابع لك أنت
**كم تستطيع أن تعطي المشروع أسبوعياً؟** التقدير أعلاه يفترض عملاً شبه متفرغ.
لو ٢٠ ساعة أسبوعياً، اضرب المدة في ٢ — **وأخبر العميل بالمدة الحقيقية لا المتفائلة.**

## ٧. الخطوة التالية

**أعطني جواب الأسئلة الثلاثة + اختيارك للمكدّس التقني**، وأطلّع لك فوراً:
1. **مخطط قاعدة البيانات كاملاً** — الجداول والحقول والعلاقات والفهارس
2. **ترحيلات (migrations) جاهزة للتشغيل**
3. **أول شاشتين تعملان**: إنشاء شحنة + قائمة الشحنات

### توصيتي للمكدّس
| الطبقة | الاقتراح | السبب |
|---|---|---|
| الخادم | **Laravel 11** | أسرع بناء للوحات الإدارية · مجتمع عربي واسع · وأنت درستَ مشروعاً كاملاً عليه |
| الواجهة | **Blade + Alpine.js** | لوحات إدارية لا SPA — أسرع وأبسط وأقل تكلفة صيانة |
| القاعدة | **MySQL 8** | ما يعرفه الجميع، ويكفي لعشرات آلاف الشحنات يومياً |
| المندوب | **صفحة ويب متجاوبة** | لا متاجر تطبيقات ولا مراجعات — وتحدّثها متى شئت |

> بدائل ممكنة إن كانت خبرتك فيها أقوى — **المهم أن تبني بما تتقنه، لا بما هو رائج.**
